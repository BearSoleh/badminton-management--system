## Admin work

Use the trusted, audited one-time bootstrap in OPERATIONS.md for the first admin; never expose bootstrap as a public route. Thereafter open **Members**. Search name/phone, choose the reviewed role/status, enter a reason and confirm the change. The backend serializes membership administration and rejects stale previews. Another active admin must change an admin's own role/status; an active administrator must remain. Pending requests can be rejected or approved. Suspended members can be reactivated. Suspension blocks new participation and offers immediately, while existing confirmed places and payment obligations remain recorded. Review affected upcoming sessions separately using the established attendance/withdrawal tools.

Open **Payment settings** to enter all three bank fields together, or clear all three. Upload only JPEG/PNG QR images up to 5 MiB. The server checks actual file bytes before attachment. Independently check the banking recipient, record a reason and check the recipient confirmation. A revision conflict requires refreshing and reviewing the current instructions; it never overwrites another admin silently. Removing/changing an image detaches the old instruction; it does not delete historical files, change charges or approve payments. Old/unattached QR objects require a trusted operator's reviewed retention cleanup. Inspect the configured private QR through the short-lived view before using real instructions.

**Overview** reports gross approved payments including historical ones, current positive unpaid/pending debt, pending full refunds, actual full refunds and gross less actual refunds. Pending receipt uploads are excluded from received money. Pending refunds have not yet been returned. Voided/superseded charges are excluded from debt. These server projections never recalculate fee snapshots. Totals use integer sen strings through display, avoiding JavaScript aggregate rounding.

**Guest access** includes original participation timestamps, retired duplicate links, charge and payment history. Existing verified linking preserves those financial records. **Audit history** filters action names with 25 records per page and shows actors/reasons/escaped metadata. Do not paste private audit payloads or phones into support chats. Phone credential changes remain intentionally blocked; do not bypass the identity guard.

## Backup, restore and ownership

The club owner is accountable for recovery and should appoint a trusted backup operator plus a second admin before real paid sessions. Record their names/contact and a secure vault location in a private operations record. Suggested pilot cadence: encrypted offsite backup daily and before migration/fee corrections, review failures daily, retain 7 daily and 4 weekly copies, and exercise restoration monthly and after backup format/provider changes. This is a manual runbook; no scheduled external backup service or retention automation has been installed.

Each recovery set needs:

- Exact app revision/migrations, project configuration, bucket policies and scheduler definition; record Auth/SMS-hook settings separately.
- Database export covering app tables, `app_private`, Auth identities/credentials and Storage metadata as required by the current provider procedure. Keep IDs/FKs and immutable fee/payment history. Back up migration history and custom managed-schema triggers/policies deliberately.
- Actual bytes from **both** private buckets, with manifest of bucket, path, object ID/version, owner, byte count, MIME and SHA-256. Freeze writes during a coordinated snapshot or reconcile objects changed during export. Metadata alone cannot recover receipt files.
- Encrypted secret/config escrow outside the database archive. Destination-specific API/signing keys, function secrets and Auth origins need separate provisioning; never publish an archive or log its contents.

Use current [Supabase backup guidance](https://supabase.com/docs/guides/platform/backups) and [CLI backup/restore instructions](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Supabase database backups exclude Storage bytes; plan the file export explicitly. The hosted restore procedure requires its own acceptance run after account access is established. Do not point the local drill at a hosted source or restore over the original project.

Run `npm run test:restore` separately from integration/live tests against the loopback BJBC stack. It refuses a source containing identities other than its own synthetic fixture or preexisting settings, creates a uniquely named empty target on ports 54420–54423, applies migrations, and restores database rows plus the local Storage filesystem snapshot. It compares 26 table snapshots, five identity mappings and two actual private objects/owners/versions/checksums, then verifies restored login, linked-member charge RLS and a signed receipt download. It removes only captured synthetic IDs/paths and removes the target stack only after asserting it is empty. A failed/nonempty target is preserved for investigation. Dumps and raw startup output are temporary ignored private artifacts; the summary contains no credentials.

For real recovery, restore into a separate verified-empty project, provision destination config/secrets, transfer files without losing identity/path ownership, revalidate byte attestations if the provider changes object identities, and compare manifests and financial balances. Exercise owner/nonowner/admin receipt access and guest/recovery expiry, verify the minute worker, and reconcile any records created after the snapshot before switching application configuration. Do not claim a successful recovery from row counts alone. Never delete the source during this process.

## Monitoring and rotation

Run `npm run health:local` for sanitized, read-only local metrics. It fails on missing RLS, an unexpected active job count, no completion within 180 seconds, worker failures or recent Cron failures. It also reports database/storage bytes, object counts, pending receipts and refunds without personal data. The hosted operator should inspect equivalent metrics privately each day and before play, alongside Auth/Edge failures and stuck payments/offers. Compare current usage with the actual provider dashboard quotas for the selected plan; no fixed quota promise or automatic paid upgrade is configured. Cron history, unattached uploads and old QR images need a reviewed retention policy that preserves receipt/audit history.

Keep backend API keys, DB passwords, signing material and deployment tokens in provider/vault secret settings. At suspected exposure, contain the cause, record affected consumers, create a replacement through the provider, update consumers, verify with synthetic permissions/payment checks, then revoke the old credential. Compromise can require immediate revocation and an outage; do not leave an exposed key active for convenience. Public publishable keys are expected in browser assets; service/secret keys bypass RLS and must stay server-side. JWT signing-key rotation and API-key rotation are distinct operations: follow [API key guidance](https://supabase.com/docs/guides/getting-started/api-keys) and [signing-key guidance](https://supabase.com/docs/guides/auth/signing-keys). Do not rotate production credentials as part of a local test.

For account recovery, follow Task 7's independent identity verification and single-use link procedure. Revoke refresh sessions where supported and verify new credentials. Existing signed access JWTs may last until their configured expiry; membership suspension still revokes protected database access immediately. Review account/admin ownership and backup access monthly and when an operator leaves. No automated secret rotation or immediate universal JWT invalidation is claimed.
