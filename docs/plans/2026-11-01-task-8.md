## Design and interfaces

- Add migration `010_admin.sql`. Active-admin RPCs own membership changes, settings and aggregates. No client direct writes, no financial snapshot recalculation. Membership actions serialize through a guard before actor locks; prevent self-demotion/suspension and removal of the last active admin. Reasons are required, unchanged request UUIDs are idempotent, stale role/status previews fail. Suspension changes access immediately through existing RLS and does not silently remove confirmed participation or payment obligations; unaccepted offers expire normally.
- Dashboard computes gross received from approved payments only (including historical payments), pending/refunded totals separately, net retained as gross minus actual refunds, and current positive unpaid/pending liabilities only. Integer sen totals are strings to avoid aggregate precision loss in JavaScript. Session/member counts are server projections, admin-only.
- Bounded member and audit pages; existing guest tools gain a scoped original participation/payment history projection. Admin navigation is a separate scrollable strip on small screens with visible keyboard focus, retaining existing links and clubhouse visual language.
- Bank settings require a reason, explicit recipient check and optimistic revision. All bank fields must be complete together or empty. QR images stay in the existing private bucket: insert-only admin policy, JPEG/PNG up to 5 MiB, actual-byte validation via new `settings-qr` Edge handler, private object/hash attestations before attachment. No external QR URLs, direct signing, metadata mutation or weakening of receipt rules.
- Pilot journey uses synthetic signup/approval, voting/queue/decline/expiry, guest participation/payment, KL late withdrawal, no-show, publication, rejection/resubmission and full approved settlement. Existing suites continue sequentially against the local database.
- Backup/restore work must include both database and actual receipt/QR bytes, a mapping/checksum manifest, identity/owner preservation and revalidation limitations. Exercise in isolated test targets only; never restore over existing development data. Recheck official provider restore instructions before implementing the drill.
- Deployment uses the specified Cloudflare Pages and Supabase stack, with private preview access protection before publishing data. Inspect available access without printing credentials; no substitute hosting. Do all local build/configuration/runbook work before reporting any missing account setup.
